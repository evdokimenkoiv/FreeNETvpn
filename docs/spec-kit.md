# Работа со Spec Kit

В репозитории закреплён **Specify CLI 1.0.6** и официальная интеграция Codex в режиме skills с Python-скриптами. На VPN-сервере этот инструмент не нужен. Для установки самого VPN используйте первую команду в [README](../README.md); эта инструкция предназначена для разработки.

Сгенерированная инфраструктура Spec Kit распространяется по [MIT-лицензии GitHub](licenses/spec-kit-MIT.txt); источник — [релиз v1.0.6](https://github.com/github/spec-kit/releases/tag/v1.0.6).

## Подготовка

Нужен Python 3.12. Из корня клона создайте отдельное окружение:

```text
python -m venv .venv
```

Ubuntu: `source .venv/bin/activate`, затем `export PYTHONUTF8=1`.

Windows PowerShell: `.\.venv\Scripts\Activate.ps1`, затем `$env:PYTHONUTF8='1'`. Если политика PowerShell запрещает активацию, добавьте интерпретатор только в PATH текущего сеанса: `$env:PATH=(Resolve-Path .venv/Scripts).Path+';'+$env:PATH`. Менять системную политику не требуется. UTF-8 нужен для вывода официальных Unicode-шаблонов в Windows-консоли.

```text
python -m pip install -r requirements-dev.txt -r requirements-speckit.txt
specify version
python tools/spec_context.py 004-spec-kit-integration
python tools/check_spec_contexts.py
python tools/spec_audit.py
```

`spec_context.py` записывает только игнорируемый `.specify/feature.json`. В Spec Kit 1.0.6 именно путь функции определяет контекст; произвольное имя Git-ветки его не заменяет. `SPECIFY_FEATURE_DIRECTORY`, если задана в окружении, имеет приоритет над файлом: удалите старое значение перед переключением через `spec_context.py`.

## Цикл разработки

В агенте, поддерживающем Codex skills, доступны `$speckit-specify`, `$speckit-clarify`, `$speckit-plan`, `$speckit-tasks`, `$speckit-analyze`, `$speckit-implement`, `$speckit-converge`. Если открытый сеанс ещё не видит новые навыки, откройте новый сеанс в этом репозитории. Исходные инструкции лежат в `.agents/skills/`; это команды агента, **не** терминальные подкоманды `specify analyze` или `specify converge`.

1. Согласуйте требования с `.specify/memory/constitution.md`; для нового изменения выполните specify → clarify по необходимости → plan.
2. Получите задачи через tasks. Укажите конкретные файлы, зависимости, проверяемые истории и условия приёмки.
3. Выполните analyze: он только читает артефакты и сообщает противоречия. Исправления выполняются отдельным шагом реализации.
4. Выполните implement, проверьте необходимые тесты и отметьте только подтверждённые задачи.
5. Выполните converge: он сопоставляет текущий код со spec/plan/tasks. При пробелах дописывает задачи в конец; после их реализации повторите converge. Чистый проход не изменяет tasks.md.

`python tools/spec_audit.py --json` — детерминированная **структурная** проверка: полнота FR/SC/AC, задачи/истории, пути и Python-символы тестов, хеши файлов официальной интеграции, открытые внешние приёмки. Наличие ссылки не доказывает успешное выполнение теста. CI не запускает LLM-анализ; семантический отчёт хранится отдельно в [spec-kit-review.md](spec-kit-review.md).

## Обновление официальной интеграции

Текущие skills и их `codex.manifest.json` получены неизменённым CLI в чистом промежуточном каталоге, где `python` доступен в PATH. Это избегает автоматической привязки генератора к `.venv/Scripts/python.exe` текущей машины. Остальная инфраструктура и существующая конституция сохранены при инициализации проекта.

Для проверки генерации в пустом временном каталоге:

```text
specify init PATH_TO_EMPTY_STAGING --integration codex --integration-options=--skills --script py --ignore-agent-tools --non-interactive
```

Не запускайте `init --force` в рабочем проекте без просмотра изменений. При обновлении версии сначала сгенерируйте интеграцию в отдельном каталоге, перенесите согласованные официальные файлы вместе с манифестами, обновите закреплённую версию и запустите проверки. Сохраняйте конституцию и спецификации. Файлы upstream не правятся вручную ради зелёных хешей.

## Проверки и внешняя приёмка

`python -m pytest -q` проверяет регрессии и контракты; CI дополнительно проверяет официальный контекст на Ubuntu/Windows, браузер и реальный трафик всех протоколов на Ubuntu 22.04/24.04. Windows предназначена для разработки, а сервер устанавливается на поддерживаемую Ubuntu.

Три внешние задачи в 001–003 остаются открытыми. Их закрывают только по [acceptance.md](acceptance.md) после тестирования независимого VPS, публичных сертификатов/портов, нативных приложений, перезагрузки и восстановления.
